## 16.1 見出しでの分割

**問題**: Markdown の回答を、`## 見出し` ごとのスライドに分けたい。見出しの前の導入文も、見出しが無い回答も扱う。

**考え方**: 見出しの**位置**を全部見つけ、「その見出しの終わり」から「次の見出しの始まり」までを本文とする。

**手順**
1. 正規表現 `(?m)^##\s+(.+)$` で、見出し行を全部見つける(位置と見出し文字)。
2. **見つからなければ**: 全体を1枚(見出し = トピック)。
3. 最初の見出しより前に文があれば、それを「導入」の1枚(見出し = トピック)。
4. 各見出し i について、本文 = 見出しの終わり ～ (次の見出しの始まり or 文末)。

**実コード**(要点のみ)
```cpp
const int bodyStart = m.capturedEnd();
const int bodyEnd = (i + 1 < matches.size()) ? matches.at(i + 1).capturedStart() : markdown.size();
slides.push_back({ m.captured(1).trimmed(), markdown.mid(bodyStart, bodyEnd - bodyStart).trimmed() });
```

**手計算**
```
導入文です。\n\n## 見出しA\n本文A\n\n## 見出しB\n本文B
→ [トピック|導入文です。] [見出しA|本文A] [見出しB|本文B]   ← 3枚
```

**計算量**: 文字数 n に対して O(n)(一度走査)。
**端の場合**: 見出し無し(1枚)/ 導入無し(最初が `##`)/ 空の本文。`### ` は `##` + 空白ではないので**当たらない**(`##` の直後は空白でなければならない)。
**テスト**: `script_composer_test.cpp` の `SplitIntoSlides*`(見出し無し → 1枚、導入が先頭に残る)。

## 16.2 貪欲法による詰め込み(200文字以内に再分割)

**問題**: 本文が長すぎるスライドを、**読みやすい長さ(200文字以内)**に分けたい。ただし**文の途中・コードの途中では切らない**。

**考え方(貪欲法)**: 先頭から順に**入る限り**詰め、入らなくなったら次の箱へ。局所的に「今入るか」だけで決める簡単な方法で、実用上十分。

**手順**(`splitLongTextSlides`)
1. 次のスライドは**そのまま通す**: 図解スライド・参考一覧・**コードフェンスを含む**もの・すでに 200 文字以下。(コードを途中で割ると、後のコード抽出が壊れるため)
2. 本文を空行(`\n{2,}`)で**段落**に分ける。
3. 段落が 200 文字を超えるなら、さらに**文**(`splitBySentence`: 句点などの境界)に分ける。
4. 部品(段落/文)を順に `current` に足す。**足すと 200 を超える**なら `current` を確定して新しい箱へ(段落の間は `\n\n` で +2 文字)。
5. 2枚目以降の見出しは `見出し（続き）`。

**実コード**(要点)
```cpp
if (!current.isEmpty() && current.size() + piece.size() + 2 > maxCharsPerSlide) {
    chunks << current;  current.clear();
}
if (!current.isEmpty()) current += "\n\n";
current += piece;
```

**手計算**(上限を 10 とし、文字数だけで考える): 部品の長さが `[4, 4, 4, 7]` のとき
- 4 を入れる(current=4)→ 次の 4: 4+4+2=10 → **超えない**(`> 10` が偽)→ current=4+2+4=10
- 次の 4: 10+4+2=16 > 10 → 確定して新しい箱(current=4)
- 7: 4+7+2=13 > 10 → 確定、新しい箱(current=7)
- 結果 `[4,4] [4] [7]` の3つ。

**計算量**: O(n)。
**限界(貪欲法の弱点)**: 全体として箱の数が最小になる保証は無い(局所判断だけ)。ここでは**最小化より、文の切れ目の自然さ**が大事なので、これで足りる。
**端の場合**: 1文だけで 200 を超える(切れない)→ そのまま 1 部品として扱う(箱が 200 を超えうる)。`pieces` が空なら元の本文。

**練習**: 上の手計算で、上限を 11 にすると何個の箱になるか(答えは章末)。

## 16.3 時間配分(比例配分と、下限を守る固定ループ)

**問題**: 動画の総フレーム数 `totalFrames` を、各スライドへ配りたい。**文字が多いスライドほど長く**、ただし **Houdini 動画ではノード 7 : ビューポート 2 : その他 1**、そして**どのスライドも読める最短(2.5秒)は確保**したい。

### (1) 基本: 重みに比例
- **重み** = `max(60, 見出しの文字数 + 本文の文字数)`(下限 60 で、極端に短いスライドが一瞬にならない)。
- **取り分** = 重み ÷ 重みの合計。**フレーム数** = 取り分 × 総フレーム数。
- **開始フレーム** = 手前までのフレーム数の**累積和**(四捨五入)。最後に `totalFrames` を**番兵**として足す(境界が n+1 個)。

**手計算**(重み 100/200/300、総 600 フレーム): 取り分 1/6, 2/6, 3/6 → 100, 200, 300 フレーム → 開始 `[0, 100, 300, 600]`。

### (2) 種類別の目標比率(Houdini モード)
種類ごとの目標 Other 0.1 / Node 0.7 / Viewport 0.2。**存在する種類の目標の合計で割り直す**(無い種類の分を、あるものへ比例配分)。種類の中では重みに比例。

**手計算**(Node・Viewport・Other が各 1 枚、重み 100、総 900 フレーム、15fps): 取り分 0.7 / 0.2 / 0.1 → 630 / 180 / 90 フレーム → 開始 `[0, 630, 810, 900]`。

### (3) 下限を守る(固定ループ)
`minFrames = min(2.5秒 × fps, 総フレーム ÷ (2n))`(2.5 秒、ただし総尺に対して非現実的に大きくならない上限)。
**「下限を下回るスライドを下限に固定し、残りのフレームを他に配り直す」を、新たに下回るものが無くなるまで繰り返す。**

```cpp
bool changed = true;
while (changed) {
    changed = false;
    // pinned な分を引いた残りを、free なスライドの取り分で配り直す
    for each slide i:
        if (pinned[i]) { frames[i] = minFrames; continue; }
        frames[i] = share[i] / freeShare * freeFrames;
        if (frames[i] < minFrames) { pinned[i] = true; changed = true; }
}
```

**手計算**(Node 1枚・Viewport 1枚・重み60の Other 8枚、総 450 フレーム、15fps)
- `minFrames = min(37.5, 450/20 = 22.5) = 22.5`
- 取り分: Other 各 0.1×(60/480)=0.0125 → 初回は 5.6 フレーム < 22.5 → **8枚とも固定**(22.5 × 8 = 180)
- 2周目: 残り 450−180=270 を Node(0.7)と Viewport(0.2)で配る → Node 270×0.7/0.9 = **210**、Viewport **60**(どちらも 22.5 以上 → 安定、ループ終了)
- 開始 `[0, 210, 270, 293, 315, 338, 360, 383, 405, 428, 450]`

**なぜ固定ループか**: 1周で「足りない分を引いて配り直す」と、**配り直した結果、別のスライドが下限を割る**ことがある。収束するまで繰り返す(固定点反復)。毎周、固定が**増えるだけ**なので、必ず終わる(最大 n 周、O(n²))。
**端の場合**: n=0(空)/ 種類が Other だけ(ratio モードにならず単純な比例)/ 総フレームが小さい(`totalFrames/(2n)` が効く)。

**練習**: 手計算(2)で、15fps・総 90 フレーム(6秒)だとどうなるか。(ヒント: `minFrames = min(37.5, 90/6=15) = 15`。答えは章末)

## 16.4 日本語の折り返し(後ろ向き探索)

**問題**: 字幕を **22 文字 × 2 行**に収めたい。ただし**「、」「。」の直後**で折りたい(単語の途中で切ると読みにくい)。**文字は1文字も落とさない**。

**考え方**: 限界の位置(22)から**後ろ向きに**探し、`、`/`。` があればその直後で切る。無ければ 22 で強制的に切る。ただし**後ろへ戻りすぎない**(半分=11 まで)。

```cpp
int cut = maxChars;
for (int i = maxChars; i >= maxChars / 2; --i) {        // 22 → 11 の順に探す
    const QChar c = rest.at(i - 1);
    if (c == QChar(0x3001) || c == QChar(0x3002)) { cut = i; break; }   // 、 または 。
}
lines << rest.left(cut);  rest = rest.mid(cut).trimmed();
```
- **最後の行は「残り全部」を取る**(`lines.size() == maxLines - 1` または残りが短い)。最大行数を守るので、**最後の行は 22 文字を超えうる**(文字を落とさない代わりに)。

**手計算**(上限 10、2 行): `これは長い文章です、ここで折れます。` (18 文字)
- 1 行目: 10→5 の順に `、` を探す。`これは長い文章です、` の 10 文字目が `、`(i=10 で即ヒット)→ 10 文字で切る
- 残り `ここで折れます。`(8文字)→ 最終行で全部取る → 2 行

**計算量**: O(n)(戻る探索は最大 maxChars/2 回)。
**テスト**: 「文字を落とさない」(行を連結すると元の文字列)。

**練習**: 句読点が全く無い 50 文字の文を 22×2 にすると、何が起こるか。(答え: 1行目22文字、2行目は残り28文字を全部取る=最終行は上限超え)

## 16.5 字幕の時刻(累積と比例配分)

**問題**: 文ごとの「いつ話し始め、いつ終わるか」を知りたい。

### クラウド/VOICEVOX(実測)
1文ずつ合成し、**各WAVのサンプル数 ÷ サンプルレート**が長さ。文の間に 0.25 秒の無音(`chunkGapSeconds`)を挟んで連結する。
- 文 i の開始 = それまでの(長さ + 無音)の**累積和**。終了 = 開始 + 自分の長さ。
- 手計算: 長さ 2.0 秒・3.0 秒・1.5 秒 → 開始 0.0 / 2.25 / 5.5、終了 2.0 / 5.25 / 7.0。

### SAPI(概算)
同期 API で文ごとの時刻が取れない。そこで**全体の長さを、文字数に比例して配分**する(約 80 文字ごとの塊 `splitIntoChunks(…, 80)`)。
```cpp
const double span = result.durationSeconds * c.size() / totalChars;
result.segments.push_back({c, cursor, cursor + span});  cursor += span;
```
- 手計算: 全体 10 秒、塊が 20/30/50 文字 → 2 / 3 / 5 秒 → 区間 [0,2] [2,5] [5,10]。
- **間(無音)や読みの速さの違いを無視するので、ずれうる** → `segmentsExact = false` で正直に伝える。

**学び**: 正確に測れない量は、**概算だと明示**する(「正確なふり」をしない)。

## 16.6 GPU リース(排他と待機)

**問題**: ナレーションとシーン描画を、**同時に GPU を使わない**ようにしたい(VRAM 不足の防止)。

**考え方**: 「貸出札は1枚」。誰かが持っている間、次に欲しい人は**寝て待つ**。返却されたら起こす。

**手順**
1. `acquire`: ロックを取る → `leaseHeld_` が false になるまで `cv_.wait` → true にして札を返す。
2. 札(`GpuLease`)がスコープを抜けると、デストラクタが `release`: ロック下で false → `notify_one`。

(コードは第15章 15.3)。

**性質**
- **相互排他**: 同時に1人だけ。
- **進行(飢餓なし?)**: `notify_one` は1人ずつ起こす。待ち手が複数でも、順番の公平性は保証されない(RAGReel は待ち手が高々2者で、逐次に呼ぶので問題にならない)。
- **デッドロック**: 同じスレッドで2回取ると自分で自分を待つ。**逐次の段**の中で1回ずつ取る設計にして避けている。

**テスト**: `resource_budget_manager_test.cpp`(2つ目が、1つ目の返却まで待たされる)。

## 16.7 ギャラリーの列数(全探索で最終段を埋める)

**問題**: n 枚のカードを、幅に応じて 3〜4 列に並べたい。**最終段が1〜2枚だけ**だと見栄えが悪い。

**考え方**: 候補の列数が**3〜4個しかない**ので、**全部試して**「最終段がいちばん埋まる列数」を選ぶ(全探索)。小さい探索空間では、賢い方法より確実。

```js
function pickColumns(count, width) {
  const max = width >= 1100 ? 4 : width >= 700 ? 3 : width >= 460 ? 2 : 1;   // 幅で上限
  const min = Math.min(3, max);                                              // 3列未満にはしない
  let best = max, bestFill = -1;
  for (let c = max; c >= min; c--) {
    const remainder = count % c;
    const fill = remainder === 0 ? 1 : remainder / c;     // 最終段の埋まり具合(割り切れれば 1)
    if (fill > bestFill + 1e-9) { best = c; bestFill = fill; }   // 同点なら、先に試した(列の多い)ほう
  }
  return best;
}
```

**手計算**(幅 1200 → max=4, min=3)
- n=24: c=4 → 余り0 → fill 1 → **4 列**
- n=25: c=4 → 余り1 → 0.25 / c=3 → 余り1 → 0.333 → **3 列**(最終段 1 枚 → 横長カードに昇格)
- n=26: c=4 → 余り2 → 0.5 / c=3 → 余り2 → 0.667 → **3 列**

**ポイント**: `1e-9` は浮動小数の誤差対策(`>` で比較するとき、ほぼ同値を同値と扱う)。「同点なら列の多いほう」を残す(ループが大きい順だから)。
**テスト**: `tools/check_gallery_layout.js`(1〜80本 × 5つの幅の**全組合せ**で、最終段が1枚だけになるときは昇格することを確認)。

**練習**: 幅 800(max=3, min=3)で n=10 は何列か。最終段は何枚か。(答え: 3列、最終段 1枚=昇格)

## 16.8 HTTP Range(区間の計算)

**問題**: 動画の途中だけを返したい(シーク)。

**仕様**: `Range: bytes=a-b`(a〜b、両端を含む)/ `bytes=a-`(a から最後まで)/ `bytes=-n`(**最後の n バイト**)。
R2 はこれを解釈して**区間**(`offset`/`length` または `suffix`)を返す。Worker はそれを `Content-Range` に直す。

```js
const r = obj.range;
const offset = r.offset !== undefined ? r.offset : Math.max(0, obj.size - r.suffix);
const length = r.length !== undefined ? r.length : obj.size - offset;
headers.set("content-range", `bytes ${offset}-${offset + length - 1}/${obj.size}`);
```

**手計算**(ファイル 1000 バイト)
- `bytes=100-199` → offset 100, length 100 → `Content-Range: bytes 100-199/1000`
- `bytes=900-` → offset 900, length 100 → `900-999/1000`
- `bytes=-50` → suffix 50 → offset = max(0, 1000−50) = 950, length 50 → `950-999/1000`
- `bytes=-5000`(ファイルより大きい)→ offset = max(0, −4000) = **0**(下限で切り詰め)→ 全体

**ポイント**: 終端は**含む**(`+ length - 1`)。off-by-one(1つずれ)の典型的な間違い所。`Accept-Ranges: bytes` を返して「対応している」と伝える。

## 16.9 ビート検出(周波数 → 周期 → 位相)

**問題**: 音楽の拍(ビート)の時刻を知りたい(場面転換を拍に合わせるため)。numpy だけで。

**考え方**: 拍は**音の立ち上がり**が**一定の間隔**で並んだもの。だから ① 立ち上がりを数値化 → ② 繰り返しの周期を探す → ③ 周期の「ずれ(位相)」を決める、の3段。

1. **立ち上がりの強さ(オンセット包絡)** `onset_envelope`
   - 短い窓(1024サンプル、256ずつずらす)で**フーリエ変換(STFT)**し、周波数ごとの強さを得る。
   - `log1p(10*強さ)` で対数に(小さな音も拾い、大きな音に潰されない)。
   - 隣の窓との**増加分だけ**(減る分は 0)を周波数で足す = **スペクトルフラックス**。音が立ち上がった瞬間に大きくなる。
   - 局所平均(21 点)を引いて、定常的な音を消す → 0〜1 に正規化。
2. **周期(テンポ)** `estimate_tempo`
   - 包絡の**自己相関**(自分を ずらして掛け合わせる)。周期ぶんずらしたとき、山が重なるので大きくなる。
   - 60〜180 BPM に対応するずらし量(ラグ)だけを調べる。**2倍のラグの値も 0.5 倍して足す**(半分のテンポと取り違えにくくする)。
   - いちばん大きいラグを選び、**放物線補間**(3点に放物線を当てて頂点を求める)で**サブフレーム精度**に。`BPM = 60 / 周期(秒)`。
3. **位相** `beat_times`
   - 周期が分かっても「最初の拍がいつか」は未定。位相(0〜周期)を細かく動かし、**拍の時刻での包絡の合計**が最大になる位相を選ぶ。

**手計算(放物線補間)**: 自己相関が ラグ 99, 100, 101 で `y0=8, y1=10, y2=9` なら、`den = y0 - 2*y1 + y2 = -3`、`shift = 0.5*(y0 - y2)/den = 0.5*(-1)/(-3) = 0.1667`。頂点は ラグ 100.17。(整数のラグだけだと精度が荒いので、補間で滑らかに)

**計算量**: STFT は窓数 × O(N log N)。自己相関は包絡の長さ L に対して O(L²)(`np.correlate`)。20 秒の曲で十分に速い。
**検証**: 既知の BPM(90〜150)の**合成曲**(キック + ハイハット)6本で誤差 1.5 BPM 以内。**答えが分かる入力を自分で作ってテストする**のが要点(`synth_click_track`)。
**場面転換を拍に寄せる**(`snap_to_beats`): 各時刻を**最も近い拍**に寄せるが、**0.6秒以内のときだけ**(遠いなら元の時刻のまま=声の途中を壊さない)。

## 16.10 しきい値で切り替わるトランジション

**問題**: 画面 A から B へ、「斜めに開く」「円が広がる」などで切り替えたい。しかも**時刻 p だけで絵が決まる**(再現でき、1コマずつ描ける)ように。

**考え方**: 画素ごとに「**いつ切り替わるか**」の**しきい値 thr(0〜1)**を持つ地図を作る。`p` が thr を超えた画素から B になる。地図の作り方で、動きの種類が決まる。

| 種類 | しきい値の作り方 |
|---|---|
| mask | `0.7·x/(w-1) + 0.3·y/(h-1)`(左上から右下へ) |
| shape | 中心からの距離 ÷ 最大距離(円が広がる) |
| liquid | `0.85·u + 0.15·波(sin)`(左から右、境界が波打つ) |
| blinds | `(y × 8 / h) mod 1`(横8段のスラット) |
| pixelate | ブロック(40px)ごとの**決まった乱数**(座標のハッシュ) |

**混ぜ方**(`feather` = 境界のぼかし幅)
```python
wgt = np.clip((p * (1 + feather) - thr) / feather, 0, 1)     # 画素ごとの B の割合
out = a * (1 - wgt) + b * wgt
```
**手計算**: thr=0.5, feather=0.1, p=0.5 → (0.5×1.1 − 0.5)/0.1 = 0.5 → A と B を半々。p=0.3 → (0.33−0.5)/0.1 = −1.7 → 0(まだ A)。p=0.9 → (0.99−0.5)/0.1 = 4.9 → 1(もう B)。
**なぜ `p*(1+feather)`**: p=1 のとき、最大のしきい値(1)の画素でも `(1.1−1)/0.1 = 1` になり、**全画素が B に完了**する。これが無いと、最後の画素が混ざったまま終わる。
**ハッシュで決まった乱数**(pixelate): `((bx × 73856093) XOR (by × 19349663)) mod 1000`(bx, by はブロックの番号)。乱数生成器の状態を持たず、**座標だけで決まる**から、何度描いても同じ(純関数)。

## 16.11 コントラスト比(相対輝度と合成)

**問題**: 文字色と背景色が読みやすいか(WCAG の 4.5:1)を、数値で確かめたい。

1. **sRGB → 線形**: 各チャンネル c(0〜1)を `c <= 0.03928 ? c/12.92 : ((c+0.055)/1.055)^2.4`(人間の目の特性に合わせたガンマの逆変換)。
2. **相対輝度** `L = 0.2126·R + 0.7152·G + 0.0722·B`(緑に最も敏感)。
3. **比** `(L明 + 0.05) / (L暗 + 0.05)`。1:1(同色)〜21:1(黒白)。
4. **半透明の色**は、背景の上に**アルファ合成**してから測る: `前景·α + 背景·(1−α)`。ダークテーマの「薄い色の面」がこれ。

**手計算**: 白(L=1)と黒(L=0): (1+0.05)/(0+0.05) = 21。灰 #767676(L≈0.181)と白: (1.05)/(0.231) = 4.54(ちょうど AA を満たす有名な灰)。
**ポイント**: 実装は `tools/check_contrast.js`。しきい値(通常文字 4.5、大きな太字 3.0)を `PAIRS` で組ごとに決める。

## 16.12 manifest の更新(読む → 足す → 書く)

```js
const manifest = await getManifest(env);
const updated = [entry, ...manifest.filter((v) => v.id !== id)];   // 同じ id を除いて、先頭に足す
await putManifest(env, updated);
```
- **冪等(べきとう)**: 同じ動画を2回送っても、結果は1件(重複しない)。
- **新しい順の維持**: 先頭に足すだけで、順序が保たれる(並べ替え不要)。
- **競合**: 「読む→書く」の間に別の更新が入ると、**後勝ちで先の更新が消える**(lost update)。一人が逐次に送る前提で許容している。直すなら **compare-and-swap(版番号の比較)**か、書き込みを1か所に直列化する(Durable Object)。
- 計算量 O(件数)。数千件までは問題にならない。

## 16.13 小さな工夫

### カウントアップの減速(イージング)
```js
const eased = 1 - Math.pow(1 - t, 3);   // easeOutCubic: 最初は速く、終わりに向かって減速
```
t=0 → 0、t=0.5 → 0.875、t=1 → 1。`t` が時間の進み具合(0〜1)。**時刻 → 値の純関数**。

### 周期のある帯の窓取り(回転寿司ベルト)
全周(皿4枚 × 8列 = 32 列)の帯を1本作り、**`(列 + offset) % 32`** で窓(40 列)を切り出す。`offset` を 1 ずつ増やすだけで**流れて見える**。32 周期で元に戻る(`offset % 32 == 0` で同じ絵 = テストで確認)。

### 最長一致(発音辞書)
辞書の語を**長い順**に置換する。`Attribute Wrangle` を先にして、短い `Wrangle` で分断されないようにする。英字は単語境界(`\b` 相当)でだけ一致(`VEX` が `VEXpression` に当たらない)。

## 16.14 アルゴリズムを選ぶ指針(このプロジェクトから)

| 状況 | 選んだ方法 | 理由 |
|---|---|---|
| 候補が数個 | **全探索**(`pickColumns`) | 単純で確実。最適性の証明が要らない |
| 局所判断で十分 | **貪欲法**(再分割) | 実装が短く、自然な切れ目を優先できる |
| 制約がぶつかる | **固定点反復**(時間配分の下限) | 収束が保証される(固定が増えるだけ) |
| 正確に測れない | **概算 + 概算だと明示**(SAPI の字幕) | 誤解を生まない |
| 再現性が欲しい | **純関数**(トランジション・ベルト) | テストしやすい・同じ入力 = 同じ出力 |
| 答えが分からない問題 | **答えの分かる入力を自作**(合成曲) | 精度を測れる |
