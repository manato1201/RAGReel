# 第11章 テストと検証

**学習目標**: ① どの道具が何を確かめるか言える ② 変更の種類ごとに、最低限動かす検査を選べる ③ 「確認した」「していない」を正しく書ける

## 11.1 検査の地図

| 道具 | 対象 | 実行 | 確かめること |
|---|---|---|---|
| `ctest`(GoogleTest 等) | C++ | `cd build; ctest --output-on-failure` | 5スイート(下) |
| `compare/tests` | Python | `cd compare; python -m unittest discover -s tests` | ビート・パイプライン・トランジション(25件) |
| `tools/check_contrast.js` | CSS の色 | `node tools/check_contrast.js` | ライト/ダークの文字×地の対比(4.5:1 など) |
| `tools/check_gallery_layout.js` | ギャラリーの列数 | `node tools/check_gallery_layout.js` | 1〜80本×5つの幅で、最終段が1枚だけにならない |
| `node --check` | JS の構文 | `node --check web/public/app.js` | 構文エラー |
| ブラウザで開く | 画面 | 手動/ヘッドレス | 実際の見え方・`file://` の挙動 |
| 本番へのHTTP | デプロイ | `fetch` で確認 | 配信内容・認証・Range(第9章) |

**C++ の5スイート**: `resource_budget_manager_test`(GPUリースの排他)/ `script_composer_tests`(スライド分割・Houdini)/ `narration_tests`(読み・字幕・クラウド音声。偽の Worker を `QTcpServer` で立てる)/ `manifest_writer_tests`(公開物。項目あり/無し・`.js` ミラー・新しい順)/ `cloud_rag_client_tests`。どれも GPU・画面不要。

## 11.2 変更の種類 → 動かす検査

| 変更 | 最低限 |
|---|---|
| スライド分割・時間配分 | `script_composer_tests` |
| 音声・辞書・字幕 | `narration_tests` |
| `metadata`/`manifest` の項目 | `manifest_writer_tests` **+ ブラウザで旧い動画と新しい動画の両方を開く** |
| CSS の色・トークン | `check_contrast.js` + ライト/ダーク両方を目で見る |
| ギャラリーの列数 | `check_gallery_layout.js` |
| `app.js` の関数 | `node --check` + `file://` で開く + 共有ギャラリー(https)でも |
| Worker | `wrangler dev` でローカル確認 → デプロイ → HTTP で確認 |
| トランジション | `compare/tests` + p=0.25/0.5/0.75 の目視 |
| ビルド設定 | **クリーンビルド**(古いキャッシュが残っていると嘘の成功になる) |

## 11.3 良いテストの形

このプロジェクトで効いたテストの共通点:

- **入力と期待値が1対1**(例: 600文字の回答が何枚になるか)。
- **端点・境界**を必ず含める(`p=0` と `p=1`、項目なし、空、上限ちょうど)。
- **「0を書かない」型の検査**: 値が不明なら項目ごと出さない(誤表示を防ぐ)。
- **純関数に切り出す**: 時間配分・字幕の折り返し・トランジション・列数の決定は、GPU・画面・ネットなしで試せる形にした(だからテストが速い)。
- **偽物を立てる**: 実際のネットに出ず、偽の HTTP サーバーでエラー系(拒否・不正な音声・到達不能)を試す。

## 11.4 実データで見つかる不具合

`--mock` の固定データでは出ない不具合が、実データで出た。

| 実データで見つかったもの | 対策 |
|---|---|
| 見出しの無い回答が1枚の長いスクロール動画になった | 3段階目の再分割(第5章) |
| 要点が重複した | 要点の抽出を見直し |
| 図に出典番号が混ざり、余計なノードが出た | `stripCitationMarkers` |
| 生のコードが読み上げられ、動画が異常に長くなった | ノード構成セクションの要約 |

> 学び: **単体テストが通っても、実データで確かめるまで「動く」とは言えない**。かといって毎回の実生成は十数分かかるので、**純関数のテスト + たまの実生成**を使い分ける。

## 11.5 「確認した」の書き方

報告・ドキュメントでは、次の3つを分けて書く。

| 書き方 | 意味 |
|---|---|
| **確認済み(何で)** | 例: 「単体テスト25件が通過」「ヘッドレス Edge で 1100px のダークを目視」 |
| **未確認(なぜ)** | 例: 「VOICEVOX の実機の時刻は、この PC に導入されていないため未確認」 |
| **既知の制限** | 例: 「静的アセットの動画は Range に 206 を返さない」 |

**やってはいけないこと**: テストが通っていないのに「完了」と書く。一部しか見ていないのに「全部確認」と書く。ビルドの「成功」通知だけを信じる(**必ずログを見る**)。

## 11.6 失敗したとき

1. **最初のエラー**を読む(後ろの大量のエラーは連鎖していることが多い)。
2. 変更を**半分に分けて**どちらが原因か絞る(二分探索)。
3. キャッシュを疑う前に、**キャッシュを消して再現するか**を確かめる(ビルド・ブラウザ・wrangler)。
4. 直したら、**その不具合を再現するテストを足す**(再発防止)。

## 演習

1. `metadata.json` に項目を足した。旧い動画で画面が壊れないことを、どう確かめるか。
2. ビルドが「成功」と通知されたが、実行ファイルが古い。何を疑うか。
3. ドキュメントに「確認した」と書くとき、何を添えるか。

## 解答(例)

1. 項目の無い `metadata.json`(旧い動画)を `output/` に残したままブラウザで開く。`manifest_writer_tests` に「値が無いとき項目を出さない」を足す。
2. 古い CMake キャッシュ・古い成果物・ログに隠れたエラー。`build/` を作り直してクリーンビルドし、**ログ**の最後まで読む。
3. 何で確認したか(テスト名・件数・環境・目視した条件)と、確認していないこと。
